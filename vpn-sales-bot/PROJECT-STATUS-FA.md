# گزارش جامع پروژه VPN Sales Bot

> تاریخ وضعیت: ۱۴۰۵/۰۶/۲۱ (2026-09-12)  
> این سند برای انتقال وضعیت پروژه به توسعه‌دهنده یا هوش مصنوعی دیگر تهیه شده است.  
> هیچ رمز عبور، توکن ربات، UUID کانفیگ یا لینک اشتراک خصوصی در این گزارش درج نشده است.

## ۱. خلاصه مدیریتی

پروژه یک MVP عملیاتی فروش VPN از طریق تلگرام است. مشتری پلن را انتخاب
می‌کند، رسید پرداخت را می‌فرستد، مدیر پرداخت را تأیید می‌کند و ربات حساب
Marzban را به‌صورت خودکار ایجاد یا تمدید می‌کند.

بخش فروش، پرداخت، ساخت حساب، تمدید، لینک HTTPS اشتراک و QR در حال کار است.
مشکل اصلی فعلی، خود ربات یا لینک اشتراک نیست: تنها سرور خروجی فعلی در ایران
قرار دارد. در نتیجه اتصال Reality برقرار می‌شود و برنامه Ping نشان می‌دهد،
اما ترافیک پس از ورود به سرور همچنان از اینترنت فیلترشده ایران خارج می‌شود.
برای عبور واقعی و سرویس مالتی‌لوکیشن باید یک یا چند Exit Node خارج ایران
اضافه شود.

## ۳. معماری فعلی

```text
مشتری تلگرام
      │
      ▼
Telegram Bot (Node.js/Telegraf)
      ├── PostgreSQL: کاربران، سفارش‌ها، پرداخت‌ها و اشتراک‌ها
      ├── Marzban API: ایجاد و تمدید حساب
      └── Telegram API از طریق Proxy محلی 127.0.0.1:8118

مشتری VPN
      ├── HTTPS Subscription روی nginx :8443
      └── VLESS/Reality روی Xray :443

n8n
      └── گزارش‌ها، یادآوری تمدید و هشدار سلامت
```

Health Server ربات فقط روی `127.0.0.1:3010` در دسترس است. PostgreSQL نیز
فقط روی localhost منتشر شده است.

## ۴. جریان خرید

1. مشتری `/start` را می‌زند.
2. پلن و پروفایل اتصال را انتخاب می‌کند.
3. ربات مبلغ و اطلاعات پرداخت را نمایش می‌دهد.
4. مشتری تصویر رسید را ارسال می‌کند.
5. مدیر رسید را با دکمه‌های تلگرام تأیید یا رد می‌کند.
6. تأیید پرداخت، سفارش را به‌صورت اتمیک وارد وضعیت Provisioning می‌کند.
7. برای سفارش جدید یک نام ترتیبی مانند `FOX1001` رزرو می‌شود.
8. حساب در Marzban ساخته و نتیجه در PostgreSQL ثبت می‌شود.
9. مشتری موارد زیر را دریافت می‌کند:
   - لینک HTTPS اشتراک؛
   - QR لینک اشتراک؛
   - کانفیگ مستقیم؛
   - QR کانفیگ مستقیم؛
   - نام حساب زیر QR.
10. حساب از بخش «سرویس‌های من» قابل مشاهده، دریافت مجدد QR و تمدید است.

## ۵. نام‌گذاری و تمدید حساب

- حساب‌های جدید از `FOX1001` آغاز می‌شوند و شماره به‌صورت اتمیک در
  PostgreSQL افزایش می‌یابد.
- هم‌زمانی دو تأیید نمی‌تواند یک نام را به دو سفارش اختصاص دهد.
- Retry ساخت سرویس، همان نام رزروشده را استفاده می‌کند.
- حساب‌های قدیمی `ct_*` تغییر نام داده یا حذف نشده‌اند.
- تمدید، همان Marzban Username و اشتراک قبلی را نگه می‌دارد.
- حجم در تمدید به حجم پلن جدید Reset می‌شود.
- اگر اشتراک هنوز فعال باشد، مدت جدید به تاریخ انقضای فعلی اضافه می‌شود.
- اگر منقضی شده باشد، مدت از زمان فعلی محاسبه می‌شود.

## ۶. تنظیم VPN فعلی

| گزینه | مقدار |
|---|---|
| Protocol | VLESS |
| Transport | TCP |
| Security | REALITY |
| Flow | `xtls-rprx-vision` |
| Port | 443 |
| Fingerprint | Chrome |
| SNI فعلی | `www.apple.com` |
| Xray Core | `26.3.27` |

این پروفایل Baseline فعلی است و بدون تست میدانی نباید حذف یا جایگزین شود.
Reality فقط ترافیک بین Client و Xray را استتار می‌کند و محل خروج اینترنت را
تغییر نمی‌دهد.

## ۷. لینک اشتراک

فرمت فعلی:

```text
https://SERVER_IP:8443/sub/{private-token}
```

- گواهی HTTPS عمومی و معتبر است.
- nginx درخواست `/sub/*` را به Marzban منتقل می‌کند.
- Endpoint قدیمی HTTP روی پورت 8090 برای سازگاری موقت باقی مانده، اما ربات
  نباید آن را برای مشتری جدید ارسال کند.
- Marzban ممکن است Token لینک اشتراک را پس از Restart تغییر دهد؛ ربات هنگام
  Startup و پیش از نمایش سرویس، URL را Sync می‌کند.
- Token اشتراک حکم رمز دسترسی را دارد و نباید عمومی شود.

## ۹. Hardening انجام‌شده

- Unique Constraint برای ارتباط هر سفارش با حداکثر یک اشتراک؛
- Unique Constraint برای Marzban Username؛
- Claim اتمیک سفارش قبل از فراخوانی Marzban؛
- بازیابی سفارش‌های گیرکرده پس از Crash؛
- Reconciliation با کاربر موجود Marzban؛
- جلوگیری از ساخت دو سرویس در Double Approval؛
- ثبت مبلغ، مدیر بررسی‌کننده، زمان بررسی و دلیل رد پرداخت؛
- Liveness بدون تماس با Dependency؛
- Readiness شامل PostgreSQL، Config و Marzban؛
- Backup فشرده PostgreSQL با Retention؛
- تولید QR به‌صورت محلی و بدون ارسال Token به سرویس خارجی؛
- `.env` در Production با Permission برابر 600؛
- عدم انتشار PostgreSQL روی اینترنت.

## ۱۱. مشکل بحرانی فعلی: خروجی داخل ایران

IP خروجی VPS فعلی از داخل ایران تشخیص داده شد:

```text
location = IR
```

نشانه‌های مشاهده‌شده:

- v2rayNG عدد Ping مثبت نمایش می‌دهد؛
- حساب Marzban فعال و منقضی‌نشده است؛
- مقدار کمی ترافیک برای Handshake ثبت می‌شود؛
- Xray و اینترنت خود سرور در دسترس‌اند؛
- سایت‌های فیلترشده برای مشتری باز نمی‌شوند.

نتیجه:

```text
Client → Reality روی VPS ایران → اینترنت فیلترشده ایران
```

Ping فقط دسترسی TCP یا اتصال اولیه را ثابت می‌کند. حتی Handshake موفق نیز
تضمین نمی‌کند که Exit Server به اینترنت بدون فیلتر دسترسی دارد. تغییر QR،
نام حساب، UUID، SNI یا پورت به‌تنهایی این مشکل معماری را حل نمی‌کند.

## ۱۲. معماری موردنیاز برای مالتی‌لوکیشن

```text
                    ┌── Exit Node خارج ایران شماره ۱
Marzban مرکزی ──────┼── Exit Node خارج ایران شماره ۲
                    └── Exit Node خارج ایران شماره ۳
                              │
                              ▼
                       اینترنت مقصد

Telegram Bot ── یک لینک Subscription ثابت ── مشتری
```

راه پیشنهادی:

1. Marzban و PostgreSQL فعلی به‌عنوان Control Plane باقی بمانند.
2. روی حداقل دو VPS خارج ایران، `Marzban-node` نصب شود.
3. هر Node دارای نام، کشور/لوکیشن، Health، اولویت و Inbound Tag یکتا باشد.
4. یک کاربر بتواند روی چند Inbound/Node کانفیگ دریافت کند.
5. لینک اشتراک مشتری ثابت بماند.
6. اضافه، حذف یا Disable کردن Node فقط محتوای لینک ساب را تغییر دهد.
7. Client با Update Subscription فهرست جدید را دریافت کند.
8. مصرف و انقضا از پنل مرکزی مدیریت شود.

برای اجرای واقعی حداقل این موارد لازم است:

- یک یا ترجیحاً دو VPS خارج ایران؛
- IP و دسترسی مدیریتی امن به VPSها؛
- کنترل DNS یک دامنه؛
- گواهی TLS برای پروفایل‌های مبتنی بر TLS؛
- بررسی Firewall و دسترسی امن Marzban-node به پنل مرکزی.

استفاده از VPS ایران به‌عنوان Relay و سپس Exit خارجی ممکن است، اما پیچیدگی،
Latency و نقطه خرابی بیشتری دارد. شروع با اتصال مستقیم Client به Nodeهای
خارجی ساده‌تر و قابل‌اندازه‌گیری‌تر است.

## ۱۳. بررسی نمونه اشتراک مالتی‌لوکیشن

نمونه خصوصی ارائه‌شده بدون افشای Credential بررسی شد:

- پاسخ HTTP موفق و دارای Headerهای Subscription بود؛
- ۲۱ کانفیگ در یک لینک ثابت ارائه می‌کرد؛
- خانواده‌های مشاهده‌شده:
  - VLESS + gRPC + REALITY؛
  - VLESS + TCP + REALITY؛
  - VLESS + gRPC + TLS؛
  - VLESS + XHTTP + TLS؛
- پورت‌های 443 و 8443 استفاده شده بودند؛
- چند Host و SNI مختلف وجود داشت.

این مشاهده فقط ساختار Subscription را نشان می‌دهد. از روی فهرست کانفیگ و
عدد Ping نمی‌توان کیفیت عبور از فیلتر، محل واقعی سرورها یا عملکرد روی همه
اپراتورهای ایران را اثبات کرد.

دامنه لینک Subscription می‌تواند پشت CDN باشد، اما این به معنی عبور اتصال
Native Reality از Cloudflare Tunnel نیست.

## ۱۴. پروفایل‌های پیشنهادی برای تست اولیه

همه پروتکل‌ها نباید هم‌زمان وارد Production شوند. برای شروع حداکثر این سه
Profile روی Node خارجی آزمایش شوند:

1. **Baseline:** VLESS + TCP + REALITY + Vision؛
2. **Fallback 1:** VLESS + XHTTP + TLS؛
3. **Fallback 2:** VLESS + gRPC + TLS.

برای هر تست ثبت شود:

```text
ISP
Network Type
شهر یا استان به‌صورت اختیاری
Profile
Client App
Connected: yes/no
Download: yes/no
Latency
Timestamp
```

نباید شماره تلفن، IP مشتری یا موقعیت دقیق ذخیره شود. تصمیم Default/Fallback
باید بر اساس داده میدانی جدید گرفته شود، نه ادعای «بهترین پروتکل ایران».

## ۱۵. تغییرات لازم در Bot برای خروجی چندکانفیگی

پایه دیتابیس `nodes` و `connection_profiles` اکنون وجود دارد، ولی جریان فعلی
هر اشتراک را عملاً به یک پروفایل اصلی متصل می‌کند. کوچک‌ترین توسعه بعدی:

1. افزودن رابطه چندبه‌چند بین اشتراک و Profileهای مجاز؛
2. دریافت لینک‌های همه Inboundهای فعال از Marzban؛
3. مرتب‌سازی بر اساس Priority؛
4. حذف خودکار Profile مربوط به Node ناسالم از خروجی؛
5. نگه‌داشتن همان URL و Token مشتری؛
6. ارسال QR لینک ساب و حداکثر دو کانفیگ منتخب.

ارسال QR جداگانه برای ۲۰ یا ۳۰ کانفیگ باعث Spam تلگرام می‌شود. در حالت
مالتی‌لوکیشن، QR اصلی باید مربوط به Subscription باشد و Client فهرست کامل را
با Update دریافت کند.

تشخیص خودکار ISP در این مرحله پیشنهاد نمی‌شود. انتخاب Profile می‌تواند
ابتدا دستی باشد.

## ۱۶. مشکلات و ریسک‌های باقی‌مانده

### اولویت بحرانی

- تنها Exit فعلی داخل ایران است و برای دور زدن فیلترینگ مناسب نیست.
- هنوز Node خارجی عملیاتی به Marzban متصل نشده است.

### اولویت بالا

- سرویس فعلی Single Node و دارای Single Point of Failure است.
- Marzban Panel روی پورت 8000 عمومی گزارش شده و بهتر است پس از بررسی دسترسی
  مدیر به localhost، VPN مدیریتی یا Firewall محدود شود.
- عملکرد پروفایل‌ها روی MCI، Irancell، Mobinnet و اینترنت ثابت هنوز Dataset
  کافی ندارد.

### اولویت متوسط

- Failover خودکار Node هنوز پیاده‌سازی نشده است.
- Health Node و حذف خودکار Config ناسالم از Subscription وجود ندارد.
- در حالت چندکانفیگی، سیاست تعداد QRهای ارسالی باید محدود شود.
- Endpoint HTTP پورت 8090 هنوز برای سازگاری قدیمی باقی مانده است.

### امنیت

- هر Subscription Token که در چت عمومی یا برای شخص ثالث ارسال شده باید
  تعویض شود.
- در صورت احتمال افشای Credential، موارد زیر دستی Rotate شوند:
  - Telegram Bot Token؛
  - رمز Marzban؛
  - رمز PostgreSQL؛
  - دسترسی root/VPS؛
  - API Keyها؛
  - Subscription Token افشاشده.
- Rotation نباید بدون برنامه انجام شود؛ ابتدا Backup و اثر آن روی سرویس‌های
  متصل بررسی شود.

## ۱۷. Backup و بازیابی

Backup دستی:

```bash
sudo /opt/vpn-sales-bot/deploy/backup-postgres.sh
```

مسیر پیش‌فرض:

```text
/var/backups/vpn-sales
```

برای تست Restore نباید دیتابیس Live بازنویسی شود. Restore باید روی دیتابیس
آزمایشی جداگانه انجام شود:

```bash
createdb vpn_sales_restore_test
pg_restore --clean --if-exists --no-owner \
  --dbname=vpn_sales_restore_test /path/to/backup.dump
```

در محیط فعلی PostgreSQL داخل Docker است؛ فرمان‌ها باید با نام Container و
Credential واقعی محیط تطبیق داده شوند، بدون چاپ رمز در Terminal یا Log.
